## 2. Business rules (confirmed with the user)

Definitions (Step 0 implements them in `server/src/lib/package-state.ts` and the new `server/src/lib/grading.ts`; the app gets them precomputed in the views):
- **Grade** (`enum Grade`): EXCELLENT, PASS, HALF, FAIL, SELF (SELF = a meeting task the owner marked done). **Full grades** = EXCELLENT, PASS, SELF → the task's points; HALF → `Math.round(points / 2)`; FAIL → 0. Rank for "the better one": full (2) > HALF (1) > FAIL (0).
- **Attempt**: one submission round of a task (第 1 次 / 第 2 次). `status` DRAFT (evidence being collected, not submitted), PENDING (「等组长审核」), GRADED. At most one attempt per task is not GRADED (the "current" attempt). This is enforced by the services under the project row lock (`lockAsMember` + the checks below), NOT by a database index: a partial index cannot be expressed in `schema.prisma`, so a later `migrate dev` would silently drop it (§3). Evidence rows belong to an attempt. Old attempts, their files, grades and notes are never deleted while the project exists (project deletion, M5, removes everything).
- **Counting attempt**: among the task's GRADED attempts, the one whose CURRENT grade (after overrides) has the best rank; on a tie the latest one (highest `no`). **Task.grade** (new column) = the counting attempt's grade, null without one. **Task.finishedAt** (new column) = when the counting grade was earned: the counting attempt's `gradedAt`, or the `createdAt` of the live (`undoneAt = null`) GradeChange that produced its current grade when that grade came from an override; null while the task is not finished. Both are recomputed by `lib/grading.ts recomputeTask()` after every grade, override, undo, meeting-done and grade-outside (`countingAttemptId` is not stored; `TaskDetail` computes it).
- **Task.status** keeps the existing enum and is now DERIVED (`statusFor()`): a PENDING attempt exists → REVIEWING; else by `grade`: full → DONE, HALF → HALF, FAIL → FAIL; else `startedAt` set → DOING, otherwise TODO. Decision (one line): the grade moves to the attempt and `Task.grade`; the status enum stays for the app's `displayStatus`, `isLocked`, `releaseTaskData` and the TasksTab mockup (🌓 rows under 待完成 with 可重交拿满); `earnedPoints` and `isFinished` move from `status` to `Task.grade` (next two items), which is what makes 「重新审核期间原来的分数不变」 AND 「拿一半算完成」 both true while a HALF task under re-review shows REVIEWING.
- **Earned points** of a task: `earnedFor(task.points, task.grade)` — full → points, HALF → `Math.round(points / 2)`, FAIL/null → 0. `earnedPoints(task)` now takes `Pick<Task, "points" | "grade">`; every caller (views, home) selects `grade`. Rescaling points (add task, edit points) keeps the grade, so earned follows the new points.
- **Finished task** (CHANGED, grade-based): `isFinished(task: Pick<Task, "status" | "grade">) = FINISHED_STATUSES.includes(task.status) || (task.grade !== null && task.grade !== "FAIL")`. Walk-through: 王子杰's task is graded HALF (finished; PREREQ_DONE went to the waiters); he resubmits → status REVIEWING, `grade` still HALF → STILL finished: the leader cannot move it (`moveTask` → TASK_FINISHED), it is never re-owned by `claimPackage` / pick-switch / swap-accept, `packageStarted` keeps his package started, `unfinishedCount` and `prereq.finished` do not flip, and when the re-review is graded PASS `becameFinished` is false so no second PREREQ_DONE goes out. Prisma fragments in package-state.ts: `FINISHED_WHERE = { OR: [{ status: { in: FINISHED_STATUSES } }, { grade: { in: ["EXCELLENT","PASS","SELF","HALF"] } }] }` and `UNFINISHED_WHERE = { status: { notIn: FINISHED_STATUSES }, OR: [{ grade: null }, { grade: "FAIL" }] }`; every query that used `status notIn FINISHED_STATUSES` uses them (packages.ts `isPackageStarted`, `claimPackage`, pick-switch; swaps.ts accept re-own; projects.ts `rescheduleTasks`; members.ts KEPT = `{ OR: [FINISHED_WHERE, { status: "REVIEWING" }] }`, RELEASED = the per-status loop over TODO/DOING/FAIL with `OR: [{ grade: null }, { grade: "FAIL" }]` added), and every query feeding `packageStarted` / `unfinishedCount` / `isOverdue` selects `grade`.
- **Locked**: status ≠ TODO or startedAt ≠ null (unchanged). A REVIEWING task that is NOT finished (first submission, or a resubmission after FAIL) is locked, not finished; leaving keeps REVIEWING tasks with their owner (M3, members.ts KEPT). What happens to a PENDING submission when such a task would change hands (leader `moveTask` into a FREE package, the owner switching packages, a newcomer picking a free package that holds it) is OPEN — §15 #1. Until it is answered, srv-tasks/srv-evidence leave those M3 code paths as they are, build no test that pins who earns the points in those three cases, and the report states the behaviour the code has (today: the attempt keeps `submittedById`, and grading credits `task.ownerId` at grading time).
- **Effective due** `effectiveDue(task, project) = task.dueAt ?? project.deadline`.
- **Overdue** (changed): not finished AND status ≠ REVIEWING AND `effectiveDue < now`. `isOverdue(task, project, now)` in package-state.ts (its `task` pick adds `grade`). Overdue wins the 🐢 emoji over TODO/DOING/FAIL (app `displayStatus`, unchanged).
- **Late** (per attempt): `submittedAt > effectiveDue` at the moment it is submitted (grade-outside and meeting-done use `now`). Shown 「迟交」; the report (M5+) counts it; a late attempt can still be graded 优秀/合格 for full points.
- **Started** (开工). `startUnderLock(tx, task, member, now): Promise<boolean>` (packages.ts, §4) has three cases: (a) `startedAt === null` → `startedAt = now`, `startedById = member.id`, TODO → DOING, void `member`'s pending swaps (reason STARTED, `voidedById = member.id`), feed TASK_STARTED; (b) `startedAt` set but `startedById !== member.id` AND `member.id === task.ownerId` (a task moved in half-done that the new owner now works on — REQUIREMENTS §13 「要你自己开始做才算」) → `startedById = member.id` only (original `startedAt` kept), void swaps and feed TASK_STARTED once, exactly as (a); (c) otherwise no-op, returns false. Callers passing the OWNER as `member`: 「开始做」 (`startTask`, which no longer returns early when `startedAt` is set — it runs case (b)), add evidence, submit, meeting-done. `gradeOutside` (a leader action) passes the owner but may only use case (a): it starts a never-started task and NEVER re-attributes `startedById` (the finished task makes the package started through `isFinished` anyway). Finishing a task (it just became finished by the predicate above) also voids the owner's pending swaps (M3 rule; `finishedEffects`, `voidedById = task.ownerId`).

Task flow (owner = `task.ownerId`; every write needs the project ACTIVE; wrong person → 403 FORBIDDEN; unknown task in this project → 404):
- **开始做** `startTask` (M3 + case (b) above): TODO → DOING, or re-attributes a moved-in task to its new owner.
- **Undo start** `undoStart`: only the owner, `startedById === owner`, status DOING, `now − startedAt ≤ 24 h` (else `UNDO_START_EXPIRED`), and the task has NO attempt rows at all (else `HAS_EVIDENCE`); not started → 409 CONFLICT. Clears the start entirely (`startedAt = startedById = null`, status TODO — also when the original `startedAt` was someone else's and the owner only re-attributed it); feed START_UNDONE (everyone sees it in 动态); bump. Pending swaps voided by the start are not restored.
- **Add evidence** (`addFileEvidence`, `addLinkEvidence`): owner only; status ≠ DONE (`TASK_DONE`); no PENDING attempt (`ALREADY_REVIEWING`: withdraw first); the current DRAFT attempt or a new one (`no = max(no) + 1`, created here) must hold < 5 items (`EVIDENCE_LIMIT`). FILE: size ≤ 10 MB (`FILE_TOO_LARGE`), sniffed type in the allow-list (`FILE_TYPE_UNSUPPORTED`), project total of FILE evidence bytes (all tasks, all attempts, counted inside the lock) + this file ≤ 50 MB (`PROJECT_STORAGE_FULL`). LINK: `http://` or `https://`, ≤ 2000 chars, parses as a URL (`INVALID_LINK`); stored name = the URL without scheme, cut to 60 chars with `…`. Adding evidence runs `startUnderLock(owner)` (cases a/b). bump. Adding to a HALF/FAIL task (a resubmission draft) keeps status HALF/FAIL until submit.
- **Delete evidence**: owner only, only from the DRAFT attempt (PENDING → `ALREADY_REVIEWING`; GRADED → 409 CONFLICT). The object is removed from storage after the transaction commits (best effort; an orphan sweep is M5). A DRAFT attempt left with 0 items stays (it is the current attempt) — the app shows `0 / 5 份`.
- **Submit** 「我做完了，请组长看」 `submitAttempt`: owner only; the DRAFT attempt exists with ≥ 1 evidence (`NO_EVIDENCE`); status ≠ DONE (`TASK_DONE`); no PENDING (`ALREADY_REVIEWING`). `startUnderLock(owner)`; sets `submittedAt = now`, `submittedById = owner`, `late`; then: owner is the LEADER → the attempt is GRADED at once with `grade = PASS`, `selfGraded = true`, `gradedById = leader`, `gradedAt = now` (「合格（组长自评）」), no SUBMITTED notification, feed GRADED (selfGraded), `recomputeTask` + finished-now effects; otherwise → PENDING, notify the leader SUBMITTED, feed SUBMITTED. Status → REVIEWING (or DONE for the leader). bump.
- **Withdraw** 「撤回修改」 `withdrawAttempt`: owner only; the PENDING attempt (guarded update, else `NOT_REVIEWING`) → DRAFT, `submittedAt = null`, `late = false`, evidence kept; status recomputed (DOING, or HALF/FAIL when an earlier attempt gave that grade); feed WITHDRAWN; bump. The leader's SUBMITTED notification stays (history); its 去评级 and the review queue then find no PENDING attempt (the app handles `?grade=1` accordingly, §10; `pendingReviews` lists PENDING attempts only, so a withdrawn one disappears from the queue on reload).
- **Grade** `gradeAttempt(grade, note?)`: leader only; the task's PENDING attempt (guarded, else `NOT_REVIEWING`); `grade` ∈ EXCELLENT | PASS | HALF | FAIL; `note` trimmed, ≤ 1000 chars, REQUIRED for HALF and FAIL (`GRADE_REASON_REQUIRED`), optional otherwise. Sets GRADED, `gradedById`, `gradedAt = now`; `recomputeTask`; finished-now effects when `becameFinished` (void owner swaps STARTED; `notifyPrereqDone`); notify the owner GRADED (never when the owner is the leader or inactive; the payload says whether this attempt is the counting one); feed GRADED; then the inactive-owner rule below; bump.
- **Grade outside** 「证据在 App 外交给我了（组长代为完成）」 `gradeOutside(grade, note?, outsideNote?)`: leader only; the task has an owner (`TASK_NO_OWNER`); no PENDING attempt (`ALREADY_REVIEWING`, copy 「TA 已经在 App 里交了，直接评级就好」); status ≠ DONE (`TASK_DONE`); grade/note rules as above; `outsideNote` optional ≤ 300 chars. Uses the DRAFT attempt when one exists (its evidence stays) else creates one; sets `outsideApp = true`, `submittedById = null`, `submittedAt = now`, `late = now > effectiveDue`, GRADED by the leader. Starts the task only when `startedAt` is null (case (a), never re-attributes). `recomputeTask`; finished-now effects; notify the owner GRADED_OUTSIDE (not when owner = leader or inactive); feed GRADED (outside); inactive-owner rule; bump.
- **Override** 「推翻评级」 `overrideGrade(grade, reason, attemptId?)`: leader only; while a PENDING attempt exists → `ALREADY_REVIEWING` (grade that one first). Target = the attempt `attemptId` names (must be a GRADED attempt of this task, else 404), default the COUNTING attempt (none → `NOT_GRADED`). So with attempt 1 = HALF (counting) and attempt 2 = FAIL, the leader can lower the HALF (default) or raise the FAIL (`attemptId`) — 「四个等级都能改，也能往下改」. `grade` ∈ the four levels (a SELF attempt can be overridden to any of them), `grade ≠ attempt.grade` (400 VALIDATION); `reason` required ≤ 1000 (`REASON_REQUIRED`). Creates `GradeChange { fromGrade, toGrade, reason, byId }`, sets `attempt.grade = toGrade`; `recomputeTask`; finished-now effects when the task just became finished; notify the owner OVERRIDDEN (not when owner = leader or inactive — the leader may override their own task); feed OVERRIDDEN; inactive-owner rule. Points follow at once (down too). The app asks again with `ConfirmSheet` before sending (界面细节: 推翻 needs a second confirmation).
- **Undo override** `undoOverride`: leader only; while a PENDING attempt exists → `ALREADY_REVIEWING` (same as override); the most recent GradeChange with `undoneAt = null` across ALL of the task's attempts (none → `NOTHING_TO_UNDO`); sets `undoneAt = now`, `undoneById`, `attempt.grade = fromGrade`; `recomputeTask`; finished-now effects; notify the owner OVERRIDDEN with `undone: true` (active owner ≠ leader only); feed OVERRIDDEN (undone); inactive-owner rule. Repeating walks back one change at a time.
- **Meeting done** 「我开完了，标记完成」 `meetingDone(summary, attendeeMemberIds)`: owner only; `task.kind === "MEETING"` (`NOT_A_MEETING`); status ≠ DONE (`TASK_DONE`); no PENDING (`ALREADY_REVIEWING`); `summary` trimmed 1–500 chars (`SUMMARY_REQUIRED`); attendees = ids of ACTIVE members of the project (unknown/inactive → 400 VALIDATION; may be empty). The owner is ALWAYS present: the server adds the owner's member id to `attendeeIds` when missing and never lists the owner as absent. Absentees are SNAPSHOTTED at completion: `absentIds` = members active at `now`, minus `attendeeIds` (so someone who joins next week is not 没来 for last week's meeting, and a later leaver stays on the list). Uses the DRAFT attempt if any else creates one; GRADED with `grade = SELF`, `meetingSummary`, `attendeeIds`, `absentIds`, `submittedById = owner`, `submittedAt = now`, `late`, `gradedById = null`. `startUnderLock(owner)`; `recomputeTask` (DONE); finished-now effects; feed MEETING_DONE with `attendeeCount = attendeeIds.length` (owner included; no notification); bump.
- **Resubmit** 「修改后重新提交」: just the normal add-evidence → submit flow on a HALF/FAIL task (attempt N+1); DONE tasks cannot resubmit (`TASK_DONE`). While the new attempt is PENDING the status is REVIEWING and `Task.grade` (HALF) keeps earning; a resubmission graded WORSE than the counting attempt (HALF then FAIL) changes nothing in `Task.grade` — the app and the GRADED notification then say so explicitly (§8, §10) instead of announcing 0 分.
- **Inactive owner after a grade-type write** (leave/removal keeps REVIEWING tasks with the leaver, members.ts KEPT; the leader may still grade them): after `gradeAttempt` / `gradeOutside` / `overrideGrade` / `undoOverride` / `recomputeTask`, when the task's owner is not an active member AND the task is not finished (grade FAIL or null), release it — `releaseTaskData` (ownerId / startedAt / startedById null; status FAIL stays, `packageId` stays null) — so the leader can move it (REQUIREMENTS §13: a leaver's 没做完的任务 become 没人负责). A finished task stays credited to the leaver. `moveTask` (M3) therefore accepts an UNFINISHED task with `packageId === null` (leaver's released task): no `from` package, `fromPackageIndex: null` in TASK_MOVED and TASK_MOVED_IN, no TASK_MOVED_OUT; finished tasks with `packageId === null` still answer TASK_FINISHED.
- **Kind** (`task.kind`) is locked once the task has an attempt that is GRADED or holds evidence: `updateActiveTask` answers `TASK_LOCKED` for `kind` then (an empty DRAFT attempt is deleted by the kind change instead — there is nothing in it). Switching a DOC task with a PENDING attempt to MEETING, or a MEETING task with a SELF attempt to DOC, is therefore impossible.

Checklist 「做到这些才算完成」 (`ChecklistItem`): per task, `text` 1–200 chars, ≤ 20 items, ordered. Replace-all edit (`PUT …/checklist`) by the leader or the task owner: items keep their `done` by id, new items start unticked, missing ids are deleted, array order = `order`. Tick (`POST …/checklist/:itemId/tick { done }`) by the owner only (leader ticking their own task is the owner case). Everyone in the project sees it. Allowed at any status. Kept so AI can prefill it later (M6).

## 3. Data model (Step 0) — migration `m4_tasks_evidence`

```ts
export type PutOptions = { mimeType: string; maxBytes: number };
export type StoredObject = { key: string; sizeBytes: number };
export class TooLargeError extends Error {}
export interface StorageProvider {
  /** Streams `body` into the object. More than `maxBytes` → throws TooLargeError and removes the partial object. */
  put(key: string, body: ReadableStream<Uint8Array> | Uint8Array, opts: PutOptions): Promise<StoredObject>;
  /** Opens the object for streaming (null when missing). */
  get(key: string): Promise<{ body: ReadableStream<Uint8Array>; sizeBytes: number } | null>;
  delete(key: string): Promise<void>;                       // missing → no-op
  deletePrefix(prefix: string): Promise<void>;              // a project's folder (M5 project deletion)
  /** A URL a browser opens WITHOUT our bearer token, valid for expiresInSec. */
  signedUrl(key: string, opts: { expiresInSec: number; fileName: string; mimeType: string; inline: boolean }): Promise<string>;
  /** Supabase later: where the app uploads directly (signed upload URL, fixed 2 h). null = upload through the API (local). */
  createDirectUpload(key: string, opts: PutOptions): Promise<{ url: string; headers: Record<string, string>; expiresAt: string } | null>;
}
export function getStorage(): StorageProvider;   // STORAGE_DRIVER=local (default) | supabase (throws "not built yet")
export const isStorageKey = (k: string) => /^[a-z0-9]+\/[a-z0-9]+\/[a-z0-9]+\.[a-z0-9]{2,5}$/.test(k);  // no "..", no leading slash
export const newFileId = () => randomBytes(12).toString("hex");   // the key's file part (matches isStorageKey; no cuid library on the server, and randomUUID has hyphens)
```

## 15. Decisions (answered by the user 2026-09-19)

1. **交了就不换手.** A task with a PENDING attempt never changes hands: `moveTask` refuses it with 409 `TASK_UNDER_REVIEW` (zh 「TA 已经交了，先评级再移」 / en "They've already submitted this. Grade it first, then move it"); switching packages, swap accept and picking/assigning a package skip such tasks (they stay owned by the submitter and get `packageId = null` when the package changes hands, exactly like a leaver's REVIEWING task); once graded, the normal rules apply (HALF/DONE are finished and never move; FAIL can move). The grade always credits the attempt's submitter because the task never left them.
2. **「我的任务」: past-due tasks that are REVIEWING or HALF go in the 「之后」 group**, sorted by due like the rest, with the right-hand date written `截止 {M月D日} · 已交` in muted grey (never red). They are not overdue.
3. **Empty prerequisite / checklist cards are shown anyway** to the owner and the leader: the 前置任务 card with only the link 「我在等别的任务…」; the checklist card with 「还没有清单，写几条「做到这些才算完成」。」 and 「编辑」. Other members see nothing when both are empty.
